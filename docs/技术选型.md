# 技术选型

## 一、架构总览

### 1.1 整体架构

项目采用 **Rust workspace monorepo** 架构，核心逻辑作为独立 crate 共享，CLI 和桌面应用作为两个 binary target 分别消费同一个 core。

```text
                         ┌──────────────────────────────────────┐
                         │          React 前端 (WebView)         │
                         │  React Flow + shadcn/ui + Zustand    │
                         └──────────────┬───────────────────────┘
                                        │ Tauri IPC (JSON)
┌──────────────┐         ┌──────────────▼───────────────────────┐
│   CLI 二进制   │         │         Tauri 桌面应用                │
│  (clap 解析)  │         │    (Tauri Commands → core 调用)      │
└──────┬───────┘         └──────────────┬───────────────────────┘
       │                                │
       └────────────┬───────────────────┘
                    │ 引用
       ┌────────────▼───────────────────────────────────────────┐
       │                    core crate                          │
       │  ┌─────────┐ ┌──────────┐ ┌──────────┐ ┌───────────┐  │
       │  │ DB 层    │ │ FFmpeg   │ │ 任务引擎  │ │ Provider  │  │
       │  │ rusqlite │ │ sidecar  │ │  tokio   │ │  抽象层   │  │
       │  └─────────┘ └──────────┘ └──────────┘ └───────────┘  │
       │  ┌─────────┐ ┌──────────┐                              │
       │  │ 文件管理 │ │ 账号管理  │                              │
       │  └─────────┘ └──────────┘                              │
       └────────────────────────────────────────────────────────┘
```

### 1.2 core crate 职责

| 模块 | 职责 |
|---|---|
| db | 数据库 schema 定义、迁移、CRUD 操作 |
| ffmpeg | FFmpeg 命令封装（裁剪/转码/合成/字幕烧录/进度解析） |
| task_engine | 异步任务调度（并发控制/重试/状态机/队列） |
| provider | 外部 AI 模型 Provider 抽象（可灵/即梦/Runway 等） |
| asset | 本地文件管理、素材归档、缩略图生成 |
| account | API Key 加密存储、用量追踪、调用日志 |
| checkpoint | 集级别版本快照（创建/恢复/清理）、项目文件备份 |

### 1.3 CLI binary 职责

基于 `clap` 解析命令行参数，直接调用 core crate 函数。适用于批量处理、自动化脚本、CI/CD 集成。

### 1.4 Tauri 桌面应用职责

通过 `#[tauri::command]` 宏将 core 函数暴露为 IPC 接口，供 React 前端调用。负责窗口管理、系统托盘、文件拖放等桌面交互。

## 三、数据模型设计

### 3.1 ER 关系总览

```text
Project 1──N Episode 1──N Shot
   │            │          │ M:N
   │            └── 1:N EpisodeCheckpoint
   │                       │
   ├── 1:N Character ──────┤ (shot_character)
   ├── 1:N Scene ──────────┤ (shot_scene)
   ├── 1:N Prop ───────────┘ (shot_prop)
   ├── 1:N Costume (→ Character)
   ├── 1:N Asset (→ Shot?)
   └── 1:N CanvasLayout (→ Episode)

Provider 1──N Model
Provider 1──N ApiAccount

Shot 1──N GenerationTask (→ Model, → ApiAccount, → Asset)
```

### 3.2 核心表定义

**Project（项目）**
- id (TEXT PK), name, description, style_prompt, global_seed, created_at, updated_at

**Episode（集/章节）**
- id, project_id (FK), title, order_index, script_text, created_at

**Shot（分镜）**
- id, episode_id (FK), order_index, summary, duration_sec, camera_angle, shot_type, mood, dialogue, video_prompt, image_prompt, status (draft/ready/generating/done), created_at

**Character（角色）**
- id, project_id (FK), name, description, appearance_prompt, reference_image_path, created_at

**Scene（场景）**
- id, project_id (FK), name, description, environment_prompt, reference_image_path, created_at

**Prop（道具）**
- id, project_id (FK), name, description, reference_image_path

**Costume（服装）**
- id, project_id (FK), character_id (FK), name, description, reference_image_path

**Asset（素材文件）**
- id, project_id (FK), shot_id (FK nullable), asset_type (image/video/audio/script), original_name, file_path（相对路径）, thumbnail_path, file_size, content_hash (SHA-256), metadata_json, created_at

**GenerationTask（生成任务）**
- id, shot_id (FK), provider_id (FK), model_id (FK), account_id (FK), task_type (text/image/video/audio), params_json, status (pending/running/success/failed/cancelled), result_asset_id (FK nullable), external_task_id, started_at, finished_at, error_message, retry_count

**Provider（模型提供商）**
- id, name, base_url, auth_type (api_key/oauth), docs_url

**Model（模型）**
- id, provider_id (FK), name, model_type (text/image/video/audio), capabilities_json, default_params_json

**ApiAccount（API 账号）**
- id, provider_id (FK), label, api_key_ref (keyring reference), usage_quota, usage_used, last_used_at, created_at

**CanvasLayout（画布布局）**
- id, episode_id (FK), nodes_json, edges_json, viewport_json, updated_at

**EpisodeCheckpoint（集版本检查点）**
- id (TEXT PK), episode_id (FK), version_number (INTEGER), label (TEXT nullable), trigger_type (TEXT: auto/manual), script_text, shots_json, canvas_nodes_json, canvas_edges_json, canvas_viewport_json, change_summary (TEXT nullable), created_at

**关联表**
- shot_character: shot_id, character_id
- shot_scene: shot_id, scene_id
- shot_prop: shot_id, prop_id

## 五、关键技术决策

### 5.1 FFmpeg Sidecar 打包策略

- 开发环境：系统安装 FFmpeg，通过 PATH 查找
- 生产构建：各平台静态编译的 FFmpeg 二进制放入 `resources/ffmpeg/`，通过 Tauri `externalBin` 配置嵌入安装包
- CLI 构建：通过环境变量 `MANGO_FFMPEG_PATH` 指定路径，或默认查找 PATH
- 使用 `ffmpeg-sidecar` crate 管理进程生命周期和输出解析

### 5.2 IPC 通信与类型对齐

- **tauri-specta（主方案）**：从 `#[tauri::command]` 自动生成完整的 TypeScript 函数绑定（包含参数和返回值类型），前端直接调用生成的类型安全函数，无需手写 `invoke()`
- **ts-rs（补充）**：对于非 command 的纯数据结构（如 Tauri event payload），标注 `#[derive(TS)]` 导出类型到 `src/lib/bindings/`
- 前端数据层：通过 TanStack Query 封装 IPC 调用，统一处理加载态、缓存、乐观更新
- 约定：所有 Tauri command 返回 `Result<T, String>`，前端统一错误处理

### 5.3 异步任务调度设计

- 基于 tokio 的 bounded channel + worker pool
- 任务状态机：Pending → Running → Success/Failed/Cancelled
- 支持并发数配置（如同时最多 3 个视频生成任务）
- 失败重试：指数退避，最大 3 次
- 进度通知：通过 Tauri event 系统推送到前端；CLI 模式下输出到 stderr

### 5.3.1 异步 DB 访问策略

- core crate 的 DB 层基于 rusqlite（同步 API），通过 `tokio-rusqlite` 包装实现异步调用
- `tokio-rusqlite` 内部维护独立线程，通过 channel 与 tokio runtime 通信，避免阻塞 async executor
- 简单查询（如 get_by_id）：直接通过 `Connection::call()` 异步执行
- 批量操作（如检查点创建）：使用事务确保原子性
- CLI 场景：仍可直接使用 rusqlite 同步 API（CLI 不需要高并发）

### 5.4 Provider 抽象层

```rust
#[async_trait]
pub trait ModelProvider: Send + Sync {
    /// 提交生成任务，返回外部任务 ID
    async fn submit(&self, params: GenerationParams) -> Result<String>;
    /// 查询任务状态
    async fn poll(&self, task_id: &str) -> Result<TaskStatus>;
    /// 取消任务
    async fn cancel(&self, task_id: &str) -> Result<()>;
    /// 下载结果
    async fn download(&self, task_id: &str, dest: &Path) -> Result<PathBuf>;
}
```

首版实现 2 个 Provider（可灵 + 即梦），后续通过实现 trait 扩展。

### 5.5 画布持久化策略

- React Flow 的 nodes/edges/viewport 状态序列化为 JSON
- 存入 CanvasLayout 表，按 episode_id 关联
- 打开项目时从 DB 恢复画布状态
- 自动保存：防抖 1 秒，变更后自动写入 DB
- 大画布优化：节点数 > 50 时使用 Web Worker 执行 JSON 序列化，避免阻塞主线程
- 增量保存策略：记录上次保存的快照哈希，仅在实际变更时写入 DB

### 5.5.1 前端状态分层

前端状态管理分为两层，职责清晰：

- **Zustand**：纯 UI 状态（侧边栏折叠、当前 Tab、画布 viewport、undo/redo 栈）
- **TanStack Query**：服务端数据状态（项目列表、角色数据、任务状态、素材列表等）
  - 自动缓存：相同 query key 的数据不重复请求
  - 乐观更新：创建/修改操作即时反映到 UI，后端确认后同步
  - 自动失效：mutation 成功后自动 invalidate 相关 query
  - 后台刷新：窗口获得焦点时自动刷新过期数据

### 5.6 版本管理策略

版本管理分为三层：

**层 1：会话内 Undo/Redo（内存）**
- Zustand + zundo（temporal middleware）实现画布和编辑器的即时撤回
- 栈深度限制 50 步，应用关闭后丢弃
- 覆盖范围：画布节点操作、剧本编辑、分镜参数修改

**层 2：EpisodeCheckpoint（集级别 JSON 快照）**
- 每个检查点完整存储一集的剧本、所有分镜、画布布局
- 不包含角色/场景快照（它们是项目级实体，避免跨集不一致）
- 恢复操作为"全量恢复"，不支持细粒度部分恢复（防止数据不一致）
- 恢复前自动创建当前状态的检查点（防止恢复后反悔）
- 触发时机：用户手动保存 / 重大操作前自动 / 定时（每 30 分钟，有变更时）
- change_summary 自动生成：对比上一版的字数差异、分镜数量变化
- 自动清理策略：24h 内保留全部，1-7 天每天保留最后一个，7 天以上每周保留最后一个，手动保存永不清理
- 角色/场景修改保护：修改前提示引用数，保存前一次的旧值支持单步撤销

**层 3：项目文件备份（SQLite 文件级复制）**
- 利用 SQLite 原生 backup API 复制整个数据库文件
- 作为项目级灾难恢复兜底
- 用户手动或每日自动触发

### 5.7 CLI 与 GUI 共享 core 的边界

- core crate 不依赖任何 Tauri API，纯 Rust 库
- core 对外暴露同步和异步两种 API（同步用于简单查询，异步用于任务提交）
- CLI 直接调用 core 函数，使用 tokio runtime
- Tauri commands 薄层封装 core 函数，仅处理 IPC 序列化和 Tauri 状态注入
- 日志通过 tracing 统一，CLI 输出到 stderr，GUI 输出到 Tauri 日志文件

### 5.8 素材管理策略

**混合存储架构**
- SQLite 只存元数据（路径、哈希、尺寸、时长等），不存二进制文件
- 素材文件统一存放在项目目录的 `assets/` 子目录下，使用 asset_id 作为文件名（不保留原始文件名）
- 缩略图存放在 `thumbnails/` 子目录，统一 webp 格式
- 所有路径使用相对路径（相对于项目根目录），项目整体移动不受影响

**项目数据目录结构**

```text
~/DVT-Projects/{project_id}/
├── project.db              # SQLite（元数据，1-10MB）
├── assets/                 # 原始素材文件
│   ├── {asset_id}.mp4
│   └── {asset_id}.png
├── thumbnails/             # 缩略图（自动生成）
│   └── {asset_id}_thumb.webp
└── exports/                # 导出成品
```

**画布拖放交互**
- 系统文件拖入：通过 Tauri `onDragDropEvent` 拦截，获取文件路径后调用后端 `import_asset`（校验 → 复制 → 缩略图 → 入库 → 返回 Asset）
- 内部面板拖入：通过 HTML5 Drag & Drop API，`dataTransfer` 携带 asset_id，在画布 `onDrop` 中创建 AssetNode
- 拖放到空白区域：创建新的 AssetNode 节点
- 拖放到已有分镜节点上：将素材绑定为该分镜的参考图/采用视频
- 视频预览：节点内只显示缩略图 + 时长，点击后在弹窗中播放（避免多 video 元素性能问题）

**素材链接断裂防护**
- 防御：asset_id 作为文件名（用户无动机修改）+ 相对路径 + content_hash 指纹
- 检测：打开项目时快速扫描所有 Asset 路径有效性（fs::exists，1000 文件 < 50ms）
- 恢复：手动重新定位（文件选择器）/ 自动哈希匹配搜索 / 批量重新定位（指定新目录）

### 5.9 国际化策略

- **方案**：react-i18next（i18next 核心 + React 绑定），React 生态最成熟的 i18n 方案
- **默认语言**：zh-CN，**支持语言**：en
- **语言检测**：i18next-browser-languagedetector 自动检测系统语言，用户手动切换后通过 localStorage 持久化
- **翻译文件组织**：`src/locales/{lang}/{namespace}.json`，静态 import 打入 bundle（桌面应用无需懒加载）
- **命名空间拆分**：按功能模块划分 —— common（通用文本）、project（项目管理）、canvas（画布）、settings（设置）等
- **初始化入口**：`src/lib/i18n.ts`，在 `main.tsx` 中 side-effect import
- **组件用法**：`useTranslation(ns)` hook + `t('key')` 函数
- **类型安全**：利用 i18next 的 TypeScript Module Augmentation，基于 zh-CN 翻译文件生成强类型 translation key，编译期发现缺失翻译
- **复数/插值**：使用 i18next 内置的 interpolation（`{{name}}`）和 pluralization 语法

## 六、风险与缓解

| 风险 | 等级 | 缓解措施 |
|---|---|---|
| Rust 开发速度慢（初期） | 高 | 先实现 DB + 1 个 Provider 跑通端到端，再扩展；使用 SeaORM 减少手写 SQL |
| WebView 跨平台不一致 | 高 | 视频统一转 H.264/MP4 预览；开发时 macOS/Windows 双平台测试 |
| FFmpeg 封装无高级库 | 高 | 基于 ffmpeg-sidecar 封装，控制在约 500-800 行；参考 LosslessCut 的实现 |
| AI Provider SDK 无 Rust 版 | 中 | 自写 HTTP 调用，参考官方 API 文档；每家约 200-300 行封装 |
| IPC 类型前后端不一致 | 中 | ts-rs 自动生成 + CI 检查类型文件是否过期 |
| 大量分镜节点画布性能 | 中 | React Flow 官方优化指南（memo + virtualization）；预计 200 节点内无问题 |
| 系统 Keychain 跨平台差异 | 低 | keyring crate 已处理三平台差异；降级方案：加密文件存储 |
| 未来插件系统受限 | 低 | V3 阶段通过 WebView 内 JS 沙箱或 WASM 模块实现 |
| 检查点 JSON 与 Schema 不兼容 | 中 | MVP 阶段 Schema 频繁变动时不建议依赖旧检查点；Schema 稳定后增加版本号标记，迁移时处理兼容性 |
| 素材文件链接断裂 | 中 | asset_id 不透明命名 + 相对路径 + content_hash；启动时快速扫描 + 自动/手动重新定位 |
